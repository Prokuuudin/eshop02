# Admin order email outbox — Plesk Scheduled Task

Этот документ описывает только запуск очереди уведомлений администратора. Включать задачу
можно лишь после применения Prisma-миграции `20261028100000_add_order_notification_outbox`
и успешной проверки приложения.

## Scheduled Task

- Тип: `Run a command`.
- Рабочий каталог: корень приложения с `package.json` и `.env.local`.
- Расписание: каждую минуту (`* * * * *`).
- Команда: `npm run notifications:admin:scheduled`.
- Одновременные запуски допустимы: строки захватываются через `FOR UPDATE SKIP LOCKED` и
  защищены lease-токеном. Зависшее задание можно перехватить через 15 минут.
- Код `0`: очередь обработана или пуста. Код `1`: назначена повторная попытка, задание
  исчерпало лимит либо сам обработчик завершился ошибкой.

Scheduled Task должен видеть те же `DATABASE_URL`, `CONTACT_TO=info@hairshop.lv` и `SMTP_*`,
что и приложение. Значения секретов не следует добавлять в команду или журналы Plesk.

## Безопасный ручной повтор

Администратор с правом `orders.update` может вызвать
`POST /api/admin/order-notifications/retry` с JSON `{ "orderId": "<id>" }`. Операция только
переводит задание со статусом `failed` обратно в `pending`, записывается в аудит и никогда
не переотправляет строку со статусом `sent`. Фактическую отправку выполняет Scheduled Task.

## Порядок включения

1. Остановить/не создавать Scheduled Task до миграции.
2. Применить миграцию через direct Neon endpoint и проверить наличие таблицы/индексов.
3. Развернуть код и проверить startup без создания заказов.
4. Создать задачу выключенной, проверить её окружение и команду.
5. Один раз запустить при пустой очереди; ожидается `claimed=0` без SMTP-вызова.
6. Включить расписание и наблюдать структурированные события `order_admin_email_*`.

Откат кода выполняется только после остановки Scheduled Task. Таблицу при аварийном откате
не удалять: в ней могут находиться ещё не отправленные задания.

## Переключение с этапа 1 и откат

Порядок обязателен: **миграция → код этапа 2 → Scheduled Task**.

- Пока работает SHA этапа 1, заказы продолжают отправлять письмо напрямую; новая пустая
  таблица никак не используется.
- Если миграция не получила блокировку за 5 секунд, она полностью откатывается. Код этапа 2
  в этом случае не разворачивать.
- Если миграция успешна, но деплой кода не состоялся, этап 1 продолжает прямую отправку, а
  новая таблица остаётся пустой и безопасной.
- После запуска кода этапа 2 прямая отправка выключена. До включения Scheduled Task задания
  накапливаются в `pending` и не теряются.
- Миграция не создаёт outbox-записи для исторических заказов этапа 1: это предотвращает
  повторную рассылку уже отправленных уведомлений.

Для отката сначала выключить расписание и дождаться завершения активного запуска. Сохранить
read-only счётчики по статусам. После возврата к SHA этапа 1 строки `pending`, `processing` и
`failed` останутся в таблице, но предыдущий код их не обработает; новые заказы снова будут
отправляться напрямую. `processing`, прерванный после принятия письма SMTP, при следующем
включении этапа 2 может дать дубль — это предел гарантии SMTP. Таблицу и её строки не удалять.
Перед повторным включением этапа 2 сверить вручную отправленные уведомления: ручная отправка
без фиксации результата в outbox создаёт риск последующего дубля.
