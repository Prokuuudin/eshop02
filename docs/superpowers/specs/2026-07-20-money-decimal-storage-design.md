# Деньги: Float → Decimal-хранение (B1 из аудита 07-20)

**Дата:** 2026-07-20
**Статус:** approved, готов к implementation plan
**Контекст:** последний пункт перепроверенного security/quality-аудита ([[project_security_audit_2026_07_20]]) — деньги в Postgres хранятся как `Float` (double precision, IEEE754 binary), а не точным decimal-типом. Явно отложен в отдельное brainstorming-обсуждение — самая инвазивная и рискованная часть аудита, живые финансовые данные.

## Scope

Только поля, которые реально хранят сумму денег (проценты/баллы/рейтинг — другая природа величины, не трогаем):

| Модель | Поля |
|---|---|
| `Invoice` | `subtotal`, `taxAmount`, `total`, `paidAmount`, `remainingAmount` |
| `Company` | `creditLimit`, `usedCredit` |
| `Product` | `price`, `oldPrice` |
| `Order` | `subtotal`, `tax`, `delivery`, `discount`, `total` |
| `ProductSubscription` | `pricePerUnit` |
| `ReturnRequest` | `refundAmount` |

Явно **не** входят в scope (другая природа, `Float` для них не проблема): `Invoice.taxRate`, `PromoCode.discount`, `PromoCode.minOrder` (это порог для сравнения, не хранимая сумма транзакции — можно перевести в отдельном будущем проходе, если понадобится), `ProductSubscription.discountPercent`, `Order.bonusSpent`/`bonusEarned` (баллы, 1 балл = 1 цент, уже целые через `Math.round`), `Product.bonusRate`, `Product.rating`.

Аудит-промпт также упоминал несуществующую модель `CreditAccount` — реальные поля живут на `Company`.

## Механизм: Postgres `numeric` + прозрачный number-интерфейс

**Что меняем:** в `prisma/schema.prisma` все 15 полей выше — `Float` → `Decimal @db.Decimal(12, 2)`. Postgres хранит их как точный `numeric` вместо `double precision` — устраняет класс багов, где даже чтение-запись без единой арифметической операции могло тихо накопить дрейф (актуально прежде всего для `Company.usedCredit` — это единственное поле-аккумулятор, `usedCredit += amount` многократно за жизнь аккаунта; `Order.total` и подобные всегда пересчитываются с нуля, поэтому для них риск ниже, но лучше унифицировать).

**Что НЕ меняем:** сам JS-расчёт (`lib/server-pricing.ts`, `lib/tax.ts`, `lib/delivery.ts`, `lib/promo-codes.ts`, `lib/bonus-program.ts`) остаётся float-арифметикой, как сейчас, с тем же округлением до цента на каждом шаге (`Math.round(x * 100) / 100`). Это сознательно узкий первый проход — чинит хранение, не трогает вычисления. Более глубокий фикс (decimal-safe арифметика внутри расчёта) — отдельная, более крупная задача на будущее, если реальная необходимость появится.

**Как не сломать существующий код:** Prisma по умолчанию возвращает `Decimal`-поля как объект `Prisma.Decimal` (обёртка над `decimal.js`), а не `number` — это сломало бы весь код, читающий эти поля (`order.total`, `product.price` и т.д. используются как `number` в ~20+ местах, включая 14+ прямых чтений `Product` без единого мэппера). Решение — Prisma Client Extension (`$extends` с `query`-компонентом, перехватывает результат любой операции к этим 6 моделям) в `lib/prisma.ts`: конвертирует `Decimal → number` через `.toNumber()` на выходе из каждого запроса, прозрачно для вызывающего кода. На запись ничего не меняется — Prisma и так принимает `number` для `Decimal`-поля на входе.

Если чистое переопределение TypeScript-типа поля через extension окажется недостижимым (типы Prisma для этих полей продолжат показывать `Decimal`) — запасной план: явный `.toNumber()` в существующих мэпперах (`mapDbToServerOrder` в `lib/orders-data-store.ts` и аналогичных для Invoice/Company), плюс тонкие read-хелперы для `Product` (сейчас читается напрямую в 14+ файлах без единого мэппера — потребуется завести такой хелпер именно для этой задачи). Это деталь имплементации, не блокирует дизайн.

## Миграция

Обычный CLI-флоу (`prisma migrate dev`) в этом репо не работает — история миграций сломана после отката variant-options ([[project_migration_workflow_broken]]). Применяем по уже отработанной ручной схеме: `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` → правим/пишем `migration.sql` вручную → `prisma db execute --file` → `prisma migrate resolve --applied`.

Каждое поле:

```sql
ALTER TABLE "Order" ALTER COLUMN "total" TYPE numeric(12,2) USING ROUND("total"::numeric, 2);
```

`ROUND(...::numeric, 2)` одновременно меняет тип и подчищает любой float-мусор за вторым знаком, если он где-то накопился за время жизни базы (не должен — приложение и так округляет до цента перед каждой записью, но `usedCredit` — кандидат на скрытый дрейф).

**Прод-риск:** `ALTER COLUMN TYPE` — полная перезапись таблицы под `ACCESS EXCLUSIVE` lock на время операции. `Order`/`Invoice`/`Company`/`ReturnRequest`/`ProductSubscription` — некрупные таблицы (сотни-тысячи строк), доли секунды. `Product` — до ~6378 строк по последним данным, тоже не должно быть заметно, но выполнить в момент низкого трафика на всякий случай.

**Порядок деплоя важен, в отличие от `Session.tokenHash`:** там `ALTER`/`DROP` были безопасны в любом порядке относительно кода, потому что старое и новое поле сосуществовали (`token` и `tokenHash` — разные колонки). Здесь же это одна и та же колонка меняет физический тип. Пока колонка ещё `double precision`, Prisma (при схеме с `Float`) отдаёт её как обычный `number` — вызывать на нём `.toNumber()` (метод `Decimal`) упадёт. Поэтому: (1) `prisma/schema.prisma` (Decimal) + `prisma generate` + extension-код деплоятся **вместе одним коммитом/деплоем**, синхронно с миграцией, а не раздельными шагами вроде A4; (2) extension пишется defensively — конвертирует в `number` только если значение реально `instanceof Prisma.Decimal`, иначе пропускает как есть. Это делает код нечувствительным к секундному зазору между «миграция применена» и «новый деплой стал живым» (тот же паттерн проверки, что уже использовали для A4/B2 — дождаться нового CSP-заголовка на проде как сигнала, что новый код живой, прежде чем считать деплой завершённым).

## Reconciliation-тест

Одноразовый скрипт (`scripts/_tmp_*.ts`, по паттерну остальных прямых обращений к Neon в этом репо):

1. **До миграции** — снэпшот всех строк всех 6 таблиц (id + денежные поля) в JSON-файл.
2. **После миграции** — перечитать те же строки, сравнить со снэпшотом с точностью до цента.
3. Любое расхождение — не падение, а построчный лог: расхождение означает, что `ROUND` тихо поправил реально накопившийся float-мусор (ожидаемо и хорошо), но полезно знать, где именно, для здравого смысла (особенно если вдруг расхождение больше цента — это уже сигнал бага, а не косметики).

## Тестирование перед деплоем

- `npm run typecheck` — ловит любые места, где TS ожидал `number`, а Prisma-типы стали показывать `Decimal` (подтверждает, нужен ли запасной план по мэпперам).
- `npm run test:unit && npm run test:integration` — 531+6 существующих тестов не должны измениться в поведении (это чисто storage-уровневая правка, бизнес-логика та же).
- Живая проверка на dev-сервере: создать заказ, посчитать сумму, сверить с `lib/tax.ts:isOrderTaxIncluded()` — эта функция уже сравнивает `order.total` с двумя реконструированными вариантами через `Math.abs(a - b) <= Math.abs(a - c)` для старых до-VAT-inclusive заказов; миграция не должна её сломать, т.к. значения не меняются семантически (только точность хранения + косметическая очистка).
