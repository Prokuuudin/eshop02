# Приглашения клиентов: держатели карты и правила получения карты

**Дата:** 2026-07-06
**Статус:** дизайн утверждён, данные карт в Neon пока отсутствуют (0 из 38 858 юзеров) — фича проектируется источник-агностично и работает по мере наполнения `User.cardNumber`.

## Задача

Разработать админ-инструмент для двух рассылок по мигрированным клиентам hairshop:

| Сегмент | Кто | Что получает |
|---|---|---|
| **A** | Клиенты с выданной картой клиента (`User.cardNumber != null`) | Email-приглашение на новый сайт для профессионалов → активация спящего аккаунта |
| **B** | Все остальные клиенты | Email с правилами получения карты клиента (карта = доступ к услугам сайта) |

Канал — только email. Телефон/SMS отложены.

## Контекст и ограничения

- В Neon мигрировано 38 858 юзеров из hairshop MSSQL (`Welcome1!`, `mustChangePassword=true`) — «спящие» аккаунты-оболочки. Ключ сопоставления — **email**.
- Номера карт в экспорте MSSQL отсутствовали ([scripts/migrate-from-mssql.ts](../../../scripts/migrate-from-mssql.ts) карту не маппил). Наполнение `cardNumber` — позже: импорт из живой БД (ERP Phase 2) или вручную админом.
- **Схему живой Neon БД не менять** — только существующие поля и `KeyValueSetting` (JSON).
- Pro-модель существующая: юзер привязан к компании (`User.companyId` + `teamRole`), карта хранится и на `User.cardNumber`, и на `Company.cardNumber`. Паттерн персональной компании мастера — как в `approveNoCardRequest` ([lib/auth.ts](../../../lib/auth.ts)).

## 1. Данные (без изменений схемы)

- **Держатель карты** = `User.cardNumber != null`.
- **Статусы приглашений (сегмент A)** — `KeyValueSetting['pro-invitations']`:
  ```json
  { "invitations": [{
      "userId": "...", "email": "...", "cardNumber": "...",
      "token": "hex32", "sentAt": "ISO", "expiresAt": "ISO",
      "acceptedAt": "ISO|null", "status": "sent|accepted|expired|error",
      "language": "ru|en|lv"
  }] }
  ```
  Паттерн идентичен `pending-registrations` в [/api/auth/register](../../../app/api/auth/register/route.ts).
- **Кампания «правила карты» (сегмент B)** — `KeyValueSetting['card-rules-campaign']`:
  ```json
  { "sentCount": 0, "errorCount": 0, "cursor": "последний обработанный userId|null", "lastRunAt": "ISO", "finished": false }
  ```

## 2. Админ-страница `/admin/invitations`

Доступ: `requireAdmin` на всех API, `AdminGate` на странице.

### Секция «Клиенты с картой» (сегмент A)

- Таблица: имя, email, № карты, статус (`—` / отправлено / зарегистрировался / просрочено), дата отправки.
- Кнопки: «Пригласить» (по одному), «Повторно» (перегенерирует токен), «Пригласить всех неприглашённых».
- Форма «Добавить карту клиенту»: email + № карты → находит юзера по email, пишет `User.cardNumber` (уникальность обеспечивает `@unique`). Юзер должен существовать; если нет — ошибка. Временная замена ERP-импорта.

### Секция «Остальные клиенты» (сегмент B)

- Сводка: «Получателей: ~N. Отправлено: X. Ошибок: Y. Статус: не начата / в процессе / завершена».
- Кнопка «Отправить» / «Продолжить»: порционная отправка ~50 писем за запрос (лимиты serverless), фронт вызывает батч-endpoint в цикле до `finished=true`. Прерывание безопасно — `cursor` позволяет продолжить.
- Фильтры получателей: `cardNumber == null`, `platformRole != 'admin'`, email непустой и не `*@client.local`.

## 3. API

| Endpoint | Метод | Что делает |
|---|---|---|
| `/api/admin/invitations` | GET | Список держателей карт + слитые статусы приглашений |
| `/api/admin/invitations` | POST | `{ userIds[] }` → генерирует токены, шлёт письма, пишет статусы |
| `/api/admin/invitations/card` | POST | `{ email, cardNumber }` → назначить карту юзеру |
| `/api/admin/card-rules-campaign` | GET | Состояние кампании B |
| `/api/admin/card-rules-campaign` | POST | Обработать следующий батч (~50), вернуть прогресс |
| `/api/auth/invite` | GET `?token=` | Валидация токена → `{ email, cardNumber, name }` для формы |
| `/api/auth/invite` | POST | `{ token, password }` → активация (см. §5) |

Админ-endpoints — `requireAdmin`. `/api/auth/invite` — публичный, токен = авторизация.

## 4. Письма

Через существующий `sendEmail` + DB-шаблоны (`email-templates-server-store`, интерполяция `{{...}}`), с хардкод-фолбэками ru/en/lv — как в [/api/admin/card-request](../../../app/api/admin/card-request/route.ts):

- **`pro-invite-{lang}`** — «Вам как держателю карты клиента — доступ к новому сайту для профессионалов». Переменные: `{{name}}`, `{{card_number}}`, `{{invite_link}}`. Ссылка `/auth/invite?token=...`, срок действия **7 дней**.
- **`card-rules-{lang}`** — правила получения карты клиента: что даёт карта, как получить (существующая форма заявки: № карты или сертификат → админ рассматривает → выдаёт карту). Переменные: `{{name}}`, `{{site_url}}`.

## 5. Приём приглашения `/auth/invite?token=`

1. Страница валидирует токен через GET `/api/auth/invite` → показывает email и № карты (read-only), поле пароля + подтверждение.
2. POST `{ token, password }` → сервер:
   - токен валиден и не просрочен, иначе ошибка «ссылка устарела»;
   - находит юзера по email из приглашения (спящий аккаунт);
   - ставит `passwordHash`, `mustChangePassword=false`, `cardNumber` из приглашения;
   - создаёт персональную компанию с этой же картой и привязывает юзера (`companyId`, `teamRole='admin'`) — по образцу `approveNoCardRequest`;
   - помечает приглашение `accepted`, создаёт сессию → клиент сразу залогинен.
3. Повторное использование токена → ошибка «уже использовано».

## 6. Ошибки и краевые случаи

- Ошибка SMTP при отправке → приглашение пишется со статусом `error`; админ видит его в списке и может повторить.
- Просроченный инвайт → статус `expired` в списке, кнопка «Повторно».
- Юзер уже активен (сам сменил пароль ранее) → активация всё равно применяет карту/компанию, пароль перезаписывает только по явному действию клиента через токен — приемлемо, токен получен только по его email.
- Батч сегмента B идемпотентен по `cursor`; двойной клик «Продолжить» не дублирует письма (сервер держит `lastRunAt`-замок на время батча).
- 38k писем упрутся в лимиты SMTP-провайдера — перед боевым запуском проверить квоты; порционность позволяет растянуть по времени.

## 7. Тестирование

- Unit: генерация/валидация/протухание токена; фильтры сегмента B; идемпотентность батча.
- E2E: админ назначает карту → приглашает → письмо (мок SMTP) → переход по токену → пароль → юзер pro и залогинен; повторный токен → ошибка.

## Вне скоупа

- SMS/телефон.
- Импорт держателей карт из живой MSSQL (ERP Phase 2) — форма ручного назначения карты закрывает разрыв.
- Отслеживание открытий писем (open tracking).
