# ERP-синк с GrinS — корректировка дизайна (топология one-way XML, не bidirectional REST)

**Дата:** 2026-07-22
**Статус:** approved, супersedes часть `2026-07-21-live-db-multistore-sync-design.md`
**Контекст:** после написания 07-21 спека получены подтверждённые ответы от владельца живой системы (GrinS, сервис на Server 2016). Реальная топология и возможности источника оказались другими, чем предполагал 07-21 дизайн. Этот документ фиксирует, что из 07-21 остаётся в силе, что отменяется, и что добавляется.

## Что подтверждено владельцем

```
GrinS / Server 2016
    → ежечасный полный XML
    → API hairshop.lv
    → обновление каталога магазина

Продажи hairshop.lv ✕ не передаются обратно в GrinS
```

- GrinS — источник цен, товаров, складских остатков.
- XML формирует сервис на Server 2016, полный дамп, раз в час.
- `warehouse id` в XML — настоящий ID склада GrinS (не наш).
- Идентификатор товара (SKU) выдаётся человеком, формат не гарантирован.
- Автоматического обмена продажами GrinS ← hairshop.lv нет.
- GrinS не даёт транзакционного механизма резервирования/decrement остатка.
- Обработка продажи в GrinS — вручную.
- Откат ошибочного импорта в GrinS сегодня = только полный restore backup.
- В исследованном XML 16 025 SKU, все уникальны.
- `<quantity>` (86 868) не равен сумме `warehouse 1-9` (79 125) для 2 133 товаров, всегда `quantity` ≥ сумма складов, обратных случаев нет — причина не выяснена.

## Что отменяется из 07-21

**Топология была спроектирована как asymmetric bidirectional (REST read-pull + синхронный write-back при заказе). Это неверно.** Источник — не REST API с пагинацией, а plain ежечасный XML-экспорт. Write-back невозможен в принципе, не «отложен до фазы 2»:

- `SYNC_WRITEBACK_ENABLED`, `lib/sync/writeback-stock.ts`, атомарный `stock -= N` эндпоинт — **не реализовывать**. GrinS не предоставляет нужной транзакции, и пока продажи всех точек (hairshop.lv, физический магазин, GrinS) не идут через общий reservation-сервис, гарантии от oversell нет в принципе — локальный decrement в eshop02 защищает только от гонки двух заказов внутри самого eshop02.
- `RestPaginatedAdapter` (курсорная пагинация) — не тот транспорт. Источник отдаёт разом весь каталог, не по страницам.
- Раздел «Rollout — Фаза 2 (write-back)» из 07-21 — удалить из плана целиком, не «выключено флагом по умолчанию».

**Что из 07-21 остаётся в силе без изменений:**

- Override-layer поверх `KeyValueSetting` (реализуется на ветке `worktree-live-db-sync-override-layer`, коммиты `d92b955`..`c1fda46`, **пока не смержена в main** — ждёт мержа независимо от write-back вопроса, это чисто admin-edit-vs-base механизм, топологии источника не касается).
- Stock исключён из override-слоя для synced-товаров — сохраняется, работает одинаково при XML-источнике.
- Никаких миграций Neon.
- Периодичность — раз в час.

## Что меняется/добавляется

### 1. Транспорт: XML/ZIP snapshot, не REST pagination

Новый адаптер — не `RestPaginatedAdapter`, а snapshot-адаптер:

```
Server 2016 / GrinS
    │ XML или ZIP + auth
    ▼
eshop02 import endpoint
    ├─ сохранить исходный файл (для rollback, см. ниже)
    ├─ проверить размер / checksum / run-идентификатор
    ├─ streaming parse (16k+ товаров, не грузить всё в память одним DOM)
    ├─ записать staging snapshot
    ├─ проверить полноту и уникальность SKU
    └─ атомарно опубликовать snapshot (или отклонить целиком)
```

`ErpAdapter`-интерфейс (`fetchPage`/`hasMore`/`nextCursor`) больше не подходит семантически — один прогон отдаёт весь каталог целиком, не постранично. Оставить `fetchPage` можно только как внутреннее чанкование уже скачанного файла (для батчинга `upsertProducts`), не как курсор по сети.

### 2. Заказ = заявка, не подтверждённая продажа

Раз остаток из XML устаревает до часа и в GrinS нет резервирования — витрина не может обещать точное наличие. Бизнес-модель:

- показывать остаток как ориентировочный;
- после оформления — ручная проверка наличия (это уже происходит в GrinS сегодня, просто явно на это полагаемся, а не изображаем real-time склад);
- не проводить необратимую оплату до подтверждения, либо уметь автоматически вернуть деньги при отсутствии товара;
- safety buffer на низких остатках:

```
XML quantity 0–2   → нет в наличии
XML quantity 3–5   → показывать не более 1
XML quantity > 5   → quantity − buffer
```

Buffer — бизнес-решение, не хардкод. **Это меняет checkout/payment-flow дизайн** (capture vs authorize, авто-возврат) — отдельный вопрос от sync-архитектуры, требует отдельной мини-спеки с владельцем перед реализацией. Здесь фиксируется только требование: не считать заказ окончательным до ручного подтверждения при текущей инфраструктуре.

### 3. Цена — не трогать, транзформации не применять

07-21 предполагал ×1.21 VAT в адаптере ([[project_erp_sync_overwrite_risk]] описывал это же для более раннего REST-дизайна) — **отменяется**. Цена уже финальная в GrinS, адаптер не должен:
- умножать на VAT;
- считать B2B-цену из розничной;
- выбирать одну цену из другой;
- переставлять приоритет `price1–price4`.

`price1`–`price4` хранить все четыре как есть. **Маппинг подтверждён владельцем 2026-07-23** (см. раздел «Ответы владельца GrinS» ниже): `price1` = розница для всех → публичная цена на eshop02. `price2` = мастера с картой клиента → кандидат на существующую card-gated B2B-цену. `price3` = отпускная цена для конкретного партнёра/дочки (Iluxsiir) — **не общий B2B-тир, не использовать как таковой**. `price4` = выставки/выездная торговля, почти не используется — игнорировать.

### 4. SKU — непрозрачная строка

- не приводить к числу;
- не резать `/`, `.`, `-`, ведущие нули;
- не менять регистр без подтверждённого правила;
- хранить исходное значение как есть;
- сравнение — точное, единообразное;
- пустой/дублирующийся SKU на входе — отклонять строку, не молча перезаписывать.

### 5. Остатки — quantity + per-warehouse раздельно

Расхождение `quantity` vs `Σ warehouse[1-9]` объяснено 2026-07-23: `quantity` включает несинхронизируемые склады 10000 (центральный) и 10008 (оптовый), которых нет в `warehouse[1-9]`. Это не ошибка данных и не десятый скрытый склад — ожидаемое поведение.

- хранить оба: общий `quantity` и все 9 `warehouse quantities` (JSON-поле или отдельная таблица);
- для отображаемого общего наличия использовать `quantity` (явное поле источника, не наша сумма);
- не показывать наличие по конкретному складу/магазину, пока не получено явное соответствие «индекс 1-9 в XML → какой из id 10001/10002/10003/10004/10005/10006/10007/10010» (владелец дал смысл id, не порядок индексов в файле — последний недостающий кусок).

### 6. Обязательные изменения в `lib/sync/sync-runner.ts` / `upsert-products.ts`

Текущий код (`sync-runner.ts:106`) вызывает `deactivateMissing` безусловно после цикла батчей, даже если часть батчей упала в `logger.recordBatchError` (run всё равно завершается как `completed`, если ни одна ошибка не была брошена наружу). Это ровно баг, который отчёт просит закрыть:

```
если errorCount > 0
    → SyncRun.status = 'failed'
    → новый snapshot НЕ публиковать
    → deactivateMissing НЕ запускать
```

Также нужны (архитектурные требования, не в этом документе — implementation plan):
- **Staging перед публикацией** — прямая запись в `Product` при потоковом парсинге живого XML недопустима (оборванный файл = смесь старых/новых данных). Нужна staging-таблица/версия snapshot с последующим atomic switch, либо snapshot-id на строке + merge на чтении.
- **Проверка полноты snapshot** — сравнение с последним успешным прогоном (не хардкод 16025): резкое падение количества, дубли SKU, отсутствие обязательных полей, доля нераспарсенных строк, snapshot старше уже применённого — всё это причины отклонить импорт целиком.
- **Атомарный lock запуска** — текущий `findFirst({status:'running'}) → create` (`sync-runner.ts:35-40`) не атомарен, гонка двух триггеров возможна. Нужен Postgres advisory lock или уникальный констрейнт на активный run.

Эти пункты — требования к будущему implementation plan синка, не к override-layer plan (`b672823`), который их не затрагивает.

### 7. Rollback / backup

Backup GrinS недостаточен как механизм отката импорта (не тестирован, время неизвестно, откат = вся БД целиком, риск потери заказов после точки backup). Для самого импорта в eshop02 нужен свой откат, независимый от backup GrinS:
- хранить несколько последних XML (исходный файл, не только распарсенное);
- checksum + статус каждого прогона;
- предыдущая опубликованная версия каталога переключаема без restore всей БД.

Отдельно (вне кода eshop02, зона ответственности владельца GrinS): зашифрованная off-site копия, задокументированный срок хранения, регулярная проверка восстановления, RPO/RTO.

### 8. Подключение третьего магазина — выбран вариант (б), реализация не определена

Владелец GrinS выбрал 2026-07-23: eshop02 забирает готовый файл из того же места, куда он уже попадает для hairshop.lv («для меня проще второе»), а не WS2016 шлёт ещё и напрямую нам. Технические детали («как для лучшей реализации — не знаю») владелец GrinS не знает — **это вопрос к владельцу backend/API hairshop.lv** (другой контакт, не тот же человек), включая формат авторизации для pull-доступа.

Простую переотправку запроса до подтверждения успешного импорта на стороне первого магазина не использовать — сбой eshop02 не должен ронять существующий hairshop.lv импорт.

### 9. Title из фида — не отображаемое имя, admin-managed по умолчанию

Подтверждено 2026-07-23: `title` в XML — служебная строка для внутреннего поиска nopCommerce (мешанина бренда + LV + EN вариантов написания), не готовое имя товара для карточки. **Не синкать `title` из фида в отображаемое `Product.title` как base-поле «синк всегда побеждает».** Дефолт: `title` остаётся полностью admin-managed, как brand/category/image/description — синк его не трогает вообще. (Альтернатива — синкать сырой `title` в отдельное служебное поле-алиас для внутреннего поиска, отображаемое имя оставить admin-полем — этот вариант сложнее и не обязателен для v1, делать только по явному запросу.)

### 10. Мусорные строки фида — pending-review для новых externalId, не auto-publish

Подтверждено 2026-07-23: в фиде реально встречаются нетоварные строки («раздел Grins для услуг/товаров вне учёта») без машиночитаемого признака в самом XML. Раз фильтровать нечем — новый `externalId`, увиденный синком впервые, не должен сразу становиться видимым на витрине. Заводить как `isActive=false`/pending, публикация — по ручному подтверждению админом. Уже известные synced-товары (сегодняшний каталог) это не трогает.

## Итог: что входит в следующий implementation plan синка

1. XML/ZIP snapshot adapter (не REST-пагинация) — streaming parse, checksum, сохранение исходника, разбор zip.
2. Staging + atomic publish, отказ от прямой записи в `Product` при парсинге.
3. `errorCount > 0` → `failed`, snapshot не публикуется, `deactivateMissing` не запускается.
4. Advisory lock на запуск синка.
5. `price1` → публичная (розничная) цена, без трансформаций. `price2` — прокинуть туда, где сегодня действует card-gated B2B-цена (нужно свериться с существующей B2B-логикой перед реализацией). `price3`/`price4` — хранить как есть, никуда не подставлять (partner-specific / почти не используется).
6. Хранение `quantity` + 9 `warehouse quantities` раздельно; расхождение объяснено (несинхронизируемые склады 10000/10008) — не баг, домысливать не нужно. Индекс 1-9 → реальный id склада ещё предстоит получить.
7. SKU как opaque string, валидация на пусто/дубли.
8. `title` из фида НЕ идёт в отображаемое `Product.title` — остаётся admin-managed, как brand/category/image/description.
9. Новый `externalId` при первом появлении — `isActive=false`/pending, не auto-publish, до ручного подтверждения админом (фид содержит нетоварный мусор без признака для фильтрации).
10. `capacity` из фида — не использовать, служебное поле GrinS для печати ценников.
11. Safety-buffer правило отображения наличия (буфер — параметр от бизнеса, ещё не согласован).
12. Локальный rollback снапшотов (последние N XML + checksum + переключаемая опубликованная версия).
13. Ручной запуск синка — уже поддержан (`runSync(..., triggeredBy: 'manual')`), сохранить в новом адаптере.
14. **Write-back не проектировать и не реализовывать** — ни сейчас, ни как флаг «выключено по умолчанию». Требует появления общей системы резервирования остатка вне scope eshop02.

Override-layer (`worktree-live-db-sync-override-layer`) — независим от всего вышеперечисленного, домержить в main отдельно.

## 2026-07-22 (продолжение): разбор реального сэмпла

Получен настоящий уменьшенный XML (`export_sample.xml`, 23 товара из 16 025, сгенерирован `generate_representative_sample.ps1` из `export.xml` — 8.77 МБ на источнике). Скрипт копирует узлы `<item>` целиком (`ImportNode($item, $true)`), не фильтрует поля — значит нижеследующий состав полей реальный, не артефакт выборки.

**Полный список полей на товар:** `sku`, `code` (штрихкод, часто пустой `<code />`, иногда мусор вроде `-4197488`), `title` (одна строка, латышский+английский/бренд смешаны через ` / `, HTML-сущности внутри — `&amp;`), `capacity`, `price1..4`, `quantity`, `warehouses/warehouse[id=1..9]`.

**Подтверждено, чего в фиде НЕТ вообще:** brand, category, image, отдельное description. Для synced-товаров это будет означать: override-layer тут не «правка побеждает пока не сброшена» — GrinS никогда не пришлёт конкурирующее значение для этих полей, так что brand/category/images/description остаются постоянно admin-only, а не временными overrides.

**SKU-примеры подтверждают opaque-string решение:** `SF0301/GL`, `F12%`, `0680.11`, `-310-051OSTER` (ведущий дефис), `395515/726` — слэши, точки, дефис в начале, спецсимволы. Не приводить к числу — решение верное, менять не надо.

**Мусорные/непрофильные строки в фиде:** `AK10` — «Klienta atlaižu karte 10%» (дисконтная карта, не товар), `HGH2121` — «HYUNDAI SANTA FE S/N: KMHSU81XDFU406815» (VIN, price1=18300, явно не товар магазина). Фид — общий инвентарный экспорт, не только «товары для сайта». В файле нет флага «показывать на сайте» — фильтрация такого мусора ложится либо на ручную курацию (isActive в eshop02), либо нужно спросить владельца, есть ли скрытое правило/список.

**Гипотеза по price1-4 (нужно подтверждение, не выдумка с нуля):** price1 ≥ price2 всегда (или равны); price3 почти всегда с длинным дробным хвостом (2.6145, 19.517505, 0.009345…) — похоже на расчётную себестоimost; price4 иногда точно равен price2, иногда 0, иногda отдельное значение. Рабочая гипотеза: price1=розница, price2=опт/мастер, price3=себестоимость, price4=акция или альтернативный опт. Не факт — спросить, но теперь можно спросить конкретно «верно ли это», а не «что это».

**Разгадка расхождения quantity vs Σwarehouse[1-9] — сузилась:** в сэмпле 5 несовпадений из 23: `6580075` (+2), `F12%` (+1), `344033` (+1000), `BALT4007` (+100), `BALT3002` (+100). Три из пяти — круглые числа (1000, 100, 100). Похоже на десятый/центральный склад или партию «в пути», не итемизированную в warehouses 1-9, а не на ошибку данных. Вопрос владельцу теперь можно сузить именно до этого.

**capacity — единицы непоследовательны:** 250 мл → `0.25`, но 1000 мл → `1000` (не `1.0`) в одном и том же сэмпле; для товаров без объёма (щипцы, ножницы) — `1`; для «1gab» (1 штука, LV) — `0.001`. Похоже на реальную неряшливость исходных данных ERP, не на нашу ошибку чтения — стоит спросить, что вообще означает `capacity` и в каких единицах.

## 2026-07-23: ответы владельца GrinS

**price1-4 — подтверждено, не гипотеза:**
- `price1` — розница для всех. **Это публичная цена для eshop02.**
- `price2` — мастера с картой клиента (профессионалы). Кандидат на существующую card-gated B2B-цену на сайте — не совпадает с моей гипотезой «опт», это именно клиент-карта.
- `price3` — цена отпуска партнёрам и дочерним компаниям (Iluxsiir). Не себестоимость, как предполагалось по дробному хвосту — это реальная отпускная цена для ОДНОГО конкретного партнёра/дочки. **Не использовать как общий B2B-тир** — не общая логика, а прайс под конкретного контрагента, которого на eshop02 нет.
- `price4` — выставки/выездная торговля, «в обычной жизни почти не используется». Игнорировать для eshop02.

**Склады — расхождение quantity vs Σwarehouse[1-9] объяснено:** это не десятый скрытый склад, а несинхронизируемые склады, которых нет в выгрузке для hairshop:

| id | склад | синк в hairshop |
|---|---|---|
| 10000 | Центральный | ✕ не синхронизируется |
| 10001 | Plavnieki | ✓ |
| 10002 | Imanta | ✓ |
| 10003 | Liepaja | ✓ |
| 10004 | Daugavpils | ✓ |
| 10005 | Riga, Rencēnu | ✓ |
| 10006 | Valmiera | ✓ |
| 10007 | Rezekne | ✓ |
| 10008 | Оптовый склад | ✕ не синхронизируется |
| 10009 | — | удалён, магазин закрыт |
| 10010 | Jelgava | ✓ |

`quantity` в XML — это остаток по ВСЕМ складам, включая 10000 и 10008. `warehouse[1-9]` в XML — только 8 синхронизируемых магазинов (10001-10007, 10010), но помечены индексами 1-9, не реальными id. **Ещё не хватает:** явного соответствия «индекс 1 в XML = какой из 10001/10002/…/10010» — владелец дал только смысл id 10000-10010, не порядок индексов 1-9 в самом файле. Это последний недостающий кусок для складской части.

**Мусорные строки — подтверждено, не баг:** «раздел Grins, в котором услуги или товары, не подлежащие хранению и учёту. НЕ ТОВАР». Причина ясна, но машиночитаемого признака в самом XML для этого нет (поля category/section в фиде не существует, см. выше) — фильтровать такие строки автоматически нечем. **Практическое решение:** не публиковать новый `externalId` на витрину автоматически при первом появлении — заводить его как `isActive=false`/pending, требовать ручного подтверждения админом перед показом на сайте. Для уже давно живущих synced-товаров это не нужно (их уже видно, что это реальные товары).

**`capacity` — подтверждено как служебное поле, eshop02 не нужно:** используется GrinS только для печати ценников (цена за литр/кг/1000мл по требованию закона), при `capacity=0` печать останавливается на «пустом товаре». Не пытаться извлечь из него единицу измерения — просто не использовать это поле вообще.

**`title` — важная находка, меняет план:** это не «человеческое название», а служебная строка для поиска nopCommerce — «раздел описания «стандарт» не показывается, если опубликованы другие языки, но в поиске со стороны клиента задействуется именно он, поэтому в него забиты все возможные и не возможные варианты, которые может набирать клиент». **Значит `title` из фида нельзя напрямую использовать как отображаемое имя товара на eshop02** — это мешанина из бренда + LV + EN вариантов написания для поискового движка другой платформы, не готовый текст для карточки товара. Практический вывод: `title` из GrinS не идёт в `Product.title` (отображаемое) базовым полем «синк всегда побеждает», а либо (а) остаётся полностью admin-managed как brand/category/image/description, либо (б) синкается в отдельное служебное поле-алиас для внутреннего поиска, а отображаемое имя — только admin. Дефолт: (а) — проще, менее рискованно показать на витрине мусор. Требует явного решения, не только моего.

**Доставка — подтверждено:** сервис на WS2016 отправляет **на HS** (hairshop.lv), приём — на API стороны сайта. Значит это push от GrinS к hairshop.lv, а не что-то, что eshop02 может сам дёрнуть напрямую у GrinS.

**Подключение eshop02 — владелец выбрал вариант (б):** «для меня проще второе» — т.е. eshop02 забирает готовый файл из того же места, куда он уже попадает для hairshop.lv, а не WS2016 шлёт ещё и нам напрямую. Технической реализации («как для лучшей реализации — не знаю») владелец GrinS не знает — **это вопрос к тому, кто держит backend/API самого hairshop.lv, не к владельцу WS2016-сервиса.** Именно там нужно узнавать формат авторизации/пути — предыдущий вопрос про auth («к чему, к файлу к API к сервису, к архиву…») владелец GrinS не понял по этой же причине: он не владеет этим куском.

**Формат — подтверждено:** архив (zip).

**Сеть — подтверждено:** «если это продолжение HS, то в Internet» — публичный доступ, VPN-блокер (как был с Neon TCP 5432) не ожидается, при условии что eshop02 подключается как «продолжение hairshop.lv», не отдельным путём к GrinS.

**Расписание — подтверждено:** не строго по часам («передача данных занимает время... можно плавать»), **и явно требуется ручной запуск** («должна быть предусмотрена возможность ручного запуска»). Уже поддержано существующим кодом — `runSync(adapter, db, triggeredBy: 'cron'|'manual'|'webhook')` в `lib/sync/sync-runner.ts` уже принимает `'manual'`, ничего дополнительно делать не нужно, только не терять эту возможность в будущем адаптере.
