# ERP-синк с GrinS — корректировка дизайна (топология one-way XML, не bidirectional REST)

**Дата:** 2026-07-22
**Статус:** approved, супersedes часть `2026-07-21-live-db-multistore-sync-design.md`
**Контекст:** после написания 07-21 спека получены подтверждённые ответы от владельца живой системы (GrinS, сервис на Server 2016). Реальная топология и возможности источника оказались другими, чем предполагал 07-21 дизайн. Этот документ фиксирует, что из 07-21 остаётся в силе, что отменяется, и что добавляется.

## Что подтверждено владельцем

```
GrinS / Server 2016
    → ежечасный полный XML
    → API hairshop.lv
    → обновление каталога магазина

Продажи hairshop.lv ✕ не передаются обратно в GrinS
```

- GrinS — источник цен, товаров, складских остатков.
- XML формирует сервис на Server 2016, полный дамп, раз в час.
- `warehouse id` в XML — настоящий ID склада GrinS (не наш).
- Идентификатор товара (SKU) выдаётся человеком, формат не гарантирован.
- Автоматического обмена продажами GrinS ← hairshop.lv нет.
- GrinS не даёт транзакционного механизма резервирования/decrement остатка.
- Обработка продажи в GrinS — вручную.
- Откат ошибочного импорта в GrinS сегодня = только полный restore backup.
- В исследованном XML 16 025 SKU, все уникальны.
- `<quantity>` (86 868) не равен сумме `warehouse 1-9` (79 125) для 2 133 товаров, всегда `quantity` ≥ сумма складов, обратных случаев нет — причина не выяснена.

## Что отменяется из 07-21

**Топология была спроектирована как asymmetric bidirectional (REST read-pull + синхронный write-back при заказе). Это неверно.** Источник — не REST API с пагинацией, а plain ежечасный XML-экспорт. Write-back невозможен в принципе, не «отложен до фазы 2»:

- `SYNC_WRITEBACK_ENABLED`, `lib/sync/writeback-stock.ts`, атомарный `stock -= N` эндпоинт — **не реализовывать**. GrinS не предоставляет нужной транзакции, и пока продажи всех точек (hairshop.lv, физический магазин, GrinS) не идут через общий reservation-сервис, гарантии от oversell нет в принципе — локальный decrement в eshop02 защищает только от гонки двух заказов внутри самого eshop02.
- `RestPaginatedAdapter` (курсорная пагинация) — не тот транспорт. Источник отдаёт разом весь каталог, не по страницам.
- Раздел «Rollout — Фаза 2 (write-back)» из 07-21 — удалить из плана целиком, не «выключено флагом по умолчанию».

**Что из 07-21 остаётся в силе без изменений:**

- Override-layer поверх `KeyValueSetting` (реализуется на ветке `worktree-live-db-sync-override-layer`, коммиты `d92b955`..`c1fda46`, **пока не смержена в main** — ждёт мержа независимо от write-back вопроса, это чисто admin-edit-vs-base механизм, топологии источника не касается).
- Stock исключён из override-слоя для synced-товаров — сохраняется, работает одинаково при XML-источнике.
- Никаких миграций Neon.
- Периодичность — раз в час.

## Что меняется/добавляется

### 1. Транспорт: XML/ZIP snapshot, не REST pagination

Новый адаптер — не `RestPaginatedAdapter`, а snapshot-адаптер:

```
Server 2016 / GrinS
    │ XML или ZIP + auth
    ▼
eshop02 import endpoint
    ├─ сохранить исходный файл (для rollback, см. ниже)
    ├─ проверить размер / checksum / run-идентификатор
    ├─ streaming parse (16k+ товаров, не грузить всё в память одним DOM)
    ├─ записать staging snapshot
    ├─ проверить полноту и уникальность SKU
    └─ атомарно опубликовать snapshot (или отклонить целиком)
```

`ErpAdapter`-интерфейс (`fetchPage`/`hasMore`/`nextCursor`) больше не подходит семантически — один прогон отдаёт весь каталог целиком, не постранично. Оставить `fetchPage` можно только как внутреннее чанкование уже скачанного файла (для батчинга `upsertProducts`), не как курсор по сети.

### 2. Заказ = заявка, не подтверждённая продажа

Раз остаток из XML устаревает до часа и в GrinS нет резервирования — витрина не может обещать точное наличие. Бизнес-модель:

- показывать остаток как ориентировочный;
- после оформления — ручная проверка наличия (это уже происходит в GrinS сегодня, просто явно на это полагаемся, а не изображаем real-time склад);
- не проводить необратимую оплату до подтверждения, либо уметь автоматически вернуть деньги при отсутствии товара;
- safety buffer на низких остатках:

```
XML quantity 0–2   → нет в наличии
XML quantity 3–5   → показывать не более 1
XML quantity > 5   → quantity − buffer
```

Buffer — бизнес-решение, не хардкод. **Это меняет checkout/payment-flow дизайн** (capture vs authorize, авто-возврат) — отдельный вопрос от sync-архитектуры, требует отдельной мини-спеки с владельцем перед реализацией. Здесь фиксируется только требование: не считать заказ окончательным до ручного подтверждения при текущей инфраструктуре.

### 3. Цена — не трогать, транзформации не применять

07-21 предполагал ×1.21 VAT в адаптере ([[project_erp_sync_overwrite_risk]] описывал это же для более раннего REST-дизайна) — **отменяется**. Цена уже финальная в GrinS, адаптер не должен:
- умножать на VAT;
- считать B2B-цену из розничной;
- выбирать одну цену из другой;
- переставлять приоритет `price1–price4`.

`price1`–`price4` хранить все четыре как есть. **Публичная (розничная) цена не назначается, пока не получена таблица соответствия** (что есть `price1..4` — розница/мастер/компания/акция). До этого момента read-pull для каталога, где меняется цена, не запускать на проде — либо запускать с `price`, замороженным на текущем Neon-значении, и подключить реальный ценовой маппинг отдельным шагом до первого боевого прогона.

### 4. SKU — непрозрачная строка

- не приводить к числу;
- не резать `/`, `.`, `-`, ведущие нули;
- не менять регистр без подтверждённого правила;
- хранить исходное значение как есть;
- сравнение — точное, единообразное;
- пустой/дублирующийся SKU на входе — отклонять строку, не молча перезаписывать.

### 5. Остатки — quantity + per-warehouse раздельно

Пока расхождение `quantity` vs `Σ warehouse[1-9]` не объяснено:
- хранить оба: общий `quantity` и все 9 `warehouse quantities` (JSON-поле или отдельная таблица);
- для отображаемого общего наличия использовать `quantity` (явное поле источника, не наша сумма);
- не показывать наличие по конкретному складу/магазину, пока нет таблицы складов и правила доступности.

### 6. Обязательные изменения в `lib/sync/sync-runner.ts` / `upsert-products.ts`

Текущий код (`sync-runner.ts:106`) вызывает `deactivateMissing` безусловно после цикла батчей, даже если часть батчей упала в `logger.recordBatchError` (run всё равно завершается как `completed`, если ни одна ошибка не была брошена наружу). Это ровно баг, который отчёт просит закрыть:

```
если errorCount > 0
    → SyncRun.status = 'failed'
    → новый snapshot НЕ публиковать
    → deactivateMissing НЕ запускать
```

Также нужны (архитектурные требования, не в этом документе — implementation plan):
- **Staging перед публикацией** — прямая запись в `Product` при потоковом парсинге живого XML недопустима (оборванный файл = смесь старых/новых данных). Нужна staging-таблица/версия snapshot с последующим atomic switch, либо snapshot-id на строке + merge на чтении.
- **Проверка полноты snapshot** — сравнение с последним успешным прогоном (не хардкод 16025): резкое падение количества, дубли SKU, отсутствие обязательных полей, доля нераспарсенных строк, snapshot старше уже применённого — всё это причины отклонить импорт целиком.
- **Атомарный lock запуска** — текущий `findFirst({status:'running'}) → create` (`sync-runner.ts:35-40`) не атомарен, гонка двух триггеров возможна. Нужен Postgres advisory lock или уникальный констрейнт на активный run.

Эти пункты — требования к будущему implementation plan синка, не к override-layer plan (`b672823`), который их не затрагивает.

### 7. Rollback / backup

Backup GrinS недостаточен как механизм отката импорта (не тестирован, время неизвестно, откат = вся БД целиком, риск потери заказов после точки backup). Для самого импорта в eshop02 нужен свой откат, независимый от backup GrinS:
- хранить несколько последних XML (исходный файл, не только распарсенное);
- checksum + статус каждого прогона;
- предыдущая опубликованная версия каталога переключаема без restore всей БД.

Отдельно (вне кода eshop02, зона ответственности владельца GrinS): зашифрованная off-site копия, задокументированный срок хранения, регулярная проверка восстановления, RPO/RTO.

### 8. Подключение третьего магазина — открытый выбор

Два варианта, решение за владельцем инфраструктуры:
1. Сервис на Server 2016 шлёт тот же XML вторым получателем — не трогает существующую интеграцию с hairshop.lv.
2. hairshop API после успешного приёма сохраняет snapshot в общее хранилище, eshop02 забирает оттуда — требует правки hairshop API, меньше риск для старой интеграции при отказе eshop02.

Простую переотправку запроса до подтверждения успешного импорта на стороне первого магазина не использовать — сбой eshop02 не должен ронять существующий hairshop.lv импорт.

## Итог: что входит в следующий implementation plan синка

1. XML/ZIP snapshot adapter (не REST-пагинация) — streaming parse, checksum, сохранение исходника.
2. Staging + atomic publish, отказ от прямой записи в `Product` при парсинге.
3. `errorCount > 0` → `failed`, snapshot не публикуется, `deactivateMissing` не запускается.
4. Advisory lock на запуск синка.
5. Хранение `price1-4` без трансформаций, розничная цена — только после получения маппинга от владельца.
6. Хранение `quantity` + 9 `warehouse quantities` раздельно, без домысливания суммы.
7. SKU как opaque string, валидация на пусто/дубли.
8. Safety-buffer правило отображения наличия (буфер — параметр от бизнеса).
9. Локальный rollback снапшотов (последние N XML + checksum + переключаемая опубликованная версия).
10. **Write-back не проектировать и не реализовывать** — ни сейчас, ни как флаг «выключено по умолчанию». Требует появления общей системы резервирования остатка вне scope eshop02.

Override-layer (`worktree-live-db-sync-override-layer`) — независим от всего вышеперечисленного, домержить в main отдельно.

## Открытые вопросы перед боевым подключением (чек-лист)

Не решаются этим документом. Разбито по адресату — часть к владельцу GrinS/hairshop.lv, часть решается внутри eshop02.

### A. Контракт данных (владелец GrinS)

1. Полный реальный XML-файл или XSD-схема — не прозы, а сырой пример на всех ~16 025 товарах (или хотя бы на 50-100 репрезентативных). Сейчас известны только названия части полей (`quantity`, `warehouse id`, `price1-4`, SKU) — нет точных тегов для title/brand/category/images/description/barcode и т.д.
2. Таблица соответствия `price1-4` → розница/мастер/компания/акция.
3. Причина расхождения `quantity` vs `Σ warehouse[1-9]` (у 2133 товаров quantity больше суммы складов).
4. `warehouse id` → человекочитаемое название склада/магазина, фиксированное число складов (всегда 9?) или может расти.
5. Гарантии по формату SKU: максимальная длина, кодировка/чарсет, может ли ID повторно использоваться после удаления товара.
6. Кодировка текстовых полей — нужен ли HTML-entity-decode как раньше, на каком языке названия (только LV или ещё RU/EN).

### B. Транспорт и авторизация (владелец GrinS / hairshop.lv API)

7. Механизм доставки точно: GrinS push'ит в hairshop API (как написано в отчёте) — значит eshop02 нужен отдельный push-получатель, или eshop02 должен сам забирать (pull) откуда-то? Один из двух вариантов подключения 3-го магазина (см. ниже, п. 12) должен быть выбран, чтобы на это ответить.
8. Формат auth для XML-эндпоинта — API-key/Basic/mTLS/IP-allowlist (пока не описан).
9. Сетевая доступность из Vercel serverless (eshop02 хостится там) — публичный HTTPS или только LAN/VPN (для сравнения: VPN исторически резал TCP 5432 к Neon — тот же риск может повториться здесь).
10. Формат передачи — сырой XML в теле ответа, ZIP-вложение, webhook POST, файл на share/SFTP?
11. Ожидаемый размер payload (сколько МБ на 16k товаров) — сверить с лимитами Vercel function (размер тела, таймаут).
12. Точность расписания — фиксированная минута часа или «примерно раз в час»? Есть ли известный разброс/задержка.

### C. Подключение третьего магазина (владелец GrinS/hairshop.lv, решение)

13. Какой из двух вариантов интеграции: (a) сервис Server 2016 шлёт тот же XML вторым получателем, (b) hairshop API складывает snapshot в общее хранилище, eshop02 забирает оттуда.
14. У кого есть доступ/полномочия менять сервис-экспортёр на Server 2016 или hairshop API, и в какие сроки.

### D. Бизнес-решения (внутри eshop02, но не техническое — нужен ответ от бизнеса)

15. Точное значение safety-buffer для полос отображения остатка (0-2/3-5/>5 — пороги предложены отчётом, буфер — нет).
16. Checkout: захват оплаты сразу или authorize-and-capture-after-confirmation? Нужен ли автовозврат при недоступности товара, и в каком окне времени.
17. Формулировка для клиента — как показывать «заказ = заявка, наличие уточняется» вместо текущего «заказ подтверждён».

### E. Эксплуатация (владелец GrinS)

18. RPO/RTO backup на стороне GrinS — сейчас восстановление не тестировано, время неизвестно, копии на том же сервере, не зашифрованы, шифрование не подтверждено.
19. Кто на связи при сбое синка / странных данных в фиде — контакт на стороне GrinS.
20. Лимиты на конкурентные запросы/нагрузку к источнику — актуально, когда к нему обращаются 3 магазина одновременно.
21. Процесс уведомления об изменении схемы фида (новое поле, переименование) — как eshop02 узнает заранее, а не постфактум по упавшему импорту.

### F. Внутреннее решение eshop02 (не внешний вопрос, но блокирует staging-часть плана)

22. Механизм staging/atomic-publish снапшота без миграции Neon (ограничение [[feedback_no_schema_changes]]) — нужен явный выбор подхода (напр. versioned blob в `KeyValueSetting` vs что-то ещё) и подтверждение пользователя перед тем, как это закладывать в план, а не просто продавливать как «само собой разумеющееся».
