# GA4: проверка перед релизом

Measurement ID: `G-P8M9PL86X1`.

## Что реализовано

- Google tag загружается только на `hairshoppro.lv` / `www.hairshoppro.lv` и только после согласия на категорию «Аналитика».
- При отзыве согласия отправка блокируется, тег удаляется из DOM, доступные `_ga*` cookies удаляются.
- App Router отправляет один ручной `page_view` на URL (RU/LV/EN); автоматический `page_view` при `config` отключён.
- Реализованы `view_item`, `add_to_cart`, `begin_checkout`, `purchase`, `sign_up` и `client_card_activation`.
- `purchase` возможен только для серверного `paymentStatus=paid`. Дедупликация выполняется по `transaction_id` в GA4 и локальной метке браузера.
- В события не передаются email, телефон, имя, адрес, номер клиентской карты или иные данные клиента.
- UTM остаются в URL первого `page_view`. При возврате Paysera используется предыдущий внутренний referrer и `ignore_referrer`; UTM не сохраняются в профиле клиента.

## Обязательные настройки GA4

1. В потоке данных GA4 открыть **Enhanced measurement → Page views → Show advanced settings** и отключить **Page changes based on browser history events**. Переходы App Router отправляются кодом; одновременно включённая автоматическая история создаст двойные `page_view`.
2. В **Data streams → Configure tag settings → List unwanted referrals** добавить домены Paysera, которые видны в реальных переходах (как минимум `paysera.com`). Это дополнительная защита атрибуции на случай нового сеанса или перехода в другом окне.
3. В **Admin → Events / Key events** отметить как key events:
   - `purchase`;
   - `sign_up`;
   - `client_card_activation` (если активация карты должна быть отдельной конверсией).
4. Проверить в Tag Assistant / DebugView на production-домене после явного тестового согласия:
   - до согласия нет запроса `gtag/js` и запросов `google-analytics.com`;
   - один `page_view` на начальную загрузку и один на каждый переход App Router;
   - RU/LV/EN URL попадают без потери языкового префикса;
   - `purchase` появляется только после серверного подтверждения оплаты и не повторяется после refresh;
   - возврат Paysera не создаёт источник `paysera.com / referral`.

## Сценарии оплаты

- **Paysera:** создание заказа не отправляет `purchase`; событие отправляется только после webhook/проверки, когда API заказа возвращает `paid`.
- **Банковский перевод и ручная оплата:** создание неоплаченного заказа не является покупкой. После подтверждения оплаты сотрудником `purchase` отправится при открытии клиентом страницы заказа.
- **Другой провайдер:** используется тот же инвариант `paymentStatus=paid`; редирект сам по себе не считается оплатой.

## Ограничение клиентской аналитики

Для банковского перевода событие отправляется при следующем открытии оплаченного заказа в браузере с аналитическим согласием. Если нужна гарантированная серверная отправка без посещения страницы, потребуется отдельный consent-aware Measurement Protocol механизм с безопасным хранением client/session ID; в эту минимальную интеграцию он намеренно не входит.
